# G4 — H-01/H-02 and H-05 security remediation, PRE-PRODUCTION

Scope: `jadeldiaz01-png/support-tickets`; stacked on audit PR #8 HEAD
`9911bf42653176d2a9cebd46d36fad503289a9e4`.

This change converts **two previously expected failures** to ordinary
failing-on-regression tests. **Do not** count CI PASS as an independent
human opinion, production authorization, or proof of immutable audit storage.

## Design
1. Add unique `(tenant_id,id)` pairs to users and tickets, then validated
   composite FKs `ticket_assignments(tenant_id,user_id)` and
   `ticket_assignments(tenant_id,ticket_id)`.
   A preflight checks all existing assignments and raises a sanitized error
   instead of rewriting any data or bypassing validation. Locks and migration
   time depend on database size and require a separate representative-restore
   rehearsal before any deployment.
2. H-05 enforces PostgreSQL audit DML append-only via a row-level
   BEFORE UPDATE/DELETE trigger and, for the runtime role, grant only SELECT
   and INSERT on the audit_events table. The CI role grants broad DML on
   other operational tables, then explicitly revokes UPDATE/DELETE/TRUNCATE
   on audit_events. Verify effective privileges in actual environments.
   The trigger protects owner DML, but owners/superusers can alter schema,
   disable the trigger or TRUNCATE. This is **not** WORM or externally immutable
   evidence. Separate tamper-evident export, backup, ownership and retention
   design is required before a stronger claim.
3. Existing routes and actor roles remain unchanged. No customer notes,
   messaging, payment actions, production config or external adapter changes.
4. Previously strict XFAIL in tests/test_g3_audit_postgres.py become normal
   PASS requirements. Additional integration tests require cross-tenant FK
   rejection, direct UPDATE rejection, runtime privileges, owner trigger
   behavior, and validated schema constraints.
5. `0005_tenant_integrity_audit_guard` migration rollback drops the trigger,
   function and the new FKs/unique constraints. CI can execute downgrade/
   replay because test database is disposable. Real rollback must separately
   consider audit risk before approval.
